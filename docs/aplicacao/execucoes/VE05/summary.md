# VE05 — Summary

VE05 (Routine by service date, direction and hour) is **partial**: the scheduled-transit model is built, wired into Compare, and independently reproduced, but no person has reviewed the itineraries, and phone performance and real-world punctuality are unmeasured. The pinned GTFS v2026.10.26 is now compacted into an on-device timetable (1,216 stop patterns, 8,417 timing profiles, 87,678 trips, none discarded) that the app resolves per date with calendars and exceptions (the 02/11 holiday swaps every weekday service for Sunday's), times past 24:00, and stops where boarding is not allowed ([roteador.ts](../../../../src/dados/transito/roteador.ts)). A new "Rotina" tab in Compare ([Rotina.tsx](../../../../src/componentes/comparar/Rotina.tsx)) takes the household profile's work/study neighbourhood or a positioned notebook destination and shows, for both homes, the door-to-door median and worst case for weekday 7–8h, weekday return 18–19h, Saturday 9–10h and late return 22–23h, the last useful return, a typical itinerary with real lines and stops, and the monthly hours difference using the profile's own days per month (Casa Forte vs Graças to central Recife: 51 vs 37 min each way, 11.5 h/month). The walk from the building uses the VE03 entrance and network, so weakly linked buildings get no time. The old "bus corridor" signal, which summed weekday, Saturday and Sunday rows from an unpinned feed (2.22× the real weekday count), now uses real weekday departures: corridor stops drop from 2,356 to 1,492, and 185 of 2,688 pilot buildings lose a corridor signal that only the inflated count supported.

Checks run: 5 new compactor tests and 19 new Jest tests covering every case in the plan's acceptance list (added and removed exceptions, Saturday and Sunday, 24:xx, opposite directions, transfer buffer, no-boarding stops, transfer penalty, last return, expired feed); Node 65/65; Jest 58/58 suites and 1,500 tests; typecheck and lint clean; v1 web smoke 50/50; rendered checks at 375 and 360 px with no overflow, page errors or external requests. G-TRANSIT has 20 cases fixed before running, and a separate Python checker that reads the raw feed confirmed every leg of all 20 (trip, route, service day, stop order, exact times, boarding rules, a feasible chain). That check caught a real defect: a query at "24:20" could not board the next service day's 01:04 trip, so the two spellings of the same instant disagreed until the router was fixed to consider the next day. The first render exposed four more, all fixed: a "last return" of 04:00 that was really the first morning bus, a garbled destination label, "1 ônibus" for metro rides, and pointless 2-minute bus hops. Cost: a 27 s pipeline, a 2.9 MB timetable payload (0.76 MB gzipped), 9–18 ms per search on desktop Node, and about 2–3 s for the whole tab in desktop Chromium. A search found no published real-time vehicle feed for Recife, so no delay figures were produced.

Decision: **iterate**. Remaining work:
- a person reviews [g-transit-revisao.csv](../../evaluation-sets/g-transit-revisao.csv) against the operator's timetables;
- time the router and the 2.9 MB payload on a low-end phone, and precompute or move the work to a worker if it is too slow;
- feed the monthly-hours difference into the Compare brief;
- use the network walk at destinations inside the pilot.

Reliability modelling waits for observed vehicle data (VE14/X09). The next eligible epoch is **VE06 (rain-aware access history)**, which builds on the VE03 network and the VE04/VE05 routes: link dated closures to the routes a home actually uses and show the alternative and its time cost.
