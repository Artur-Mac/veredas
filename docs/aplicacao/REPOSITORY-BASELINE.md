## Architecture decisions the plan should make explicitly

1. Keep the app as the local comparison and explanation client. Perform bulk acquisition, geometry preparation, extraction and source reconciliation offline. Ship compact versioned partitions. A model call or portal scrape must not be required to render an already saved comparison.
2. Build one reusable evidence ledger and one insight resolver. Raw records retain source, observed time, publication time, retrieval time, spatial reference, parser version and content hash. A linked fact records the relation and its derivation; a route fact records start, end, time, mode and graph version. An insight is a deterministic projection over selected facts and the current pair of properties.
3. Use explicit states for unknown, absent, stale, disputed and unsupported. They are primarily engineering states; the main UI should provide concise conclusions and a short optional source drawer. Do not scatter repeated generic warnings through the experience.
4. Existing `contratos.ts` uses strict Zod objects. Do not append new fields to stored analyses without versioning. A feature bundle keyed by building/edge/source can evolve separately from the user's notebook. Preserve `null` semantics and unit/period information.
5. Prefer a small tabular spatial pipeline and cached graph to a distributed graph database. Choose a database or routing engine only when the epoch's dataset size and query need justify it. Implementation choices should be recorded, not assumed to be findings from the literature.
6. Device-private routine destinations can be applied locally to precomputed reachability or a downloadable graph. If later routing needs a server, specify request minimization, retention, deletion and whether user coordinates leave the device. Do not pool notes/photos from personal notebooks as training data by default.
7. Retain the 72-neighborhood base index and add a capability matrix by neighborhood/building. Enhanced pilot coverage and municipal base coverage are separate concepts.

## Concrete inherited weaknesses that should become baseline tests

- Two data systems coexisted: `docs/dados/infra/scripts` (archived in `ignorar/dados-pipeline-2026-11-11/` on 18 Nov 2026) produced exploratory files, while `scripts/dados` builds what `src/dados/recife` publishes. A successful HTTP response or exploratory `ok` status is not proof of parsed entities, useful geolocation or app publication.
- The HTTP client, now `scripts/dados/http.mjs`, already caches, retries selected status codes, honors a bounded `Retry-After`, checks `no-store`/`private`, and uses atomic file writes. Reuse these behaviors. The separate cache downloader in `scripts/dados/camadas-inteligentes-recife.mjs` returns an existing file indefinitely and writes raw responses directly, so freshness, completeness and atomicity are not uniformly enforced.
- The integrated audit records GTFS rows being summed across service calendars, wrongly described as daily activity. Rebuild scheduled departures by service date, exceptions, direction, and time window. Test midnight-crossing service times and original coordinates. Never restore the known erroneous coordinate shift.
- Defesa Civil CSV structure and administrative/event time differ across years. A parser must identify semantic columns using fixtures for each version and quarantine unknown formats rather than accepting displaced cells.
- The reported 2,622 buildings within 50 m of their official street geometry are a useful association result, not 2,622 verified entrances. Routing must distinguish a building centroid, frontage, public entrance, side of street and legal crossing.
- A nearby destination is not necessarily open, reachable or publicly accessible. The failed Maps/Overpass collection is not a zero-amenity observation. CNEFE's reduced three-category layer cannot supply all everyday needs.
- Surface temperature, a coarse surface elevation grid, and one heritage tree are not respectively indoor temperature, curb height, or canopy coverage. Existing data support broader spatial comparisons; the new UI needs quantities that the actual model computes.
- `custoPorPartes.ts` includes fixed electricity/transport assumptions and a purchase/legal-cost scenario. Its assumptions, effective dates, and financial field meanings need a separate audit before turning them into a stronger financial recommendation. Record behavior as-is; do not silently broaden the claim.
- Comments in `src/componentes/comparar/comparar.ts` say the comparison never recommends. `tests/perfil-domicilio-custo.test.ts` includes a prohibited-word list. These are legacy product choices, not reasons to refuse the user's current request for decision support. Update obsolete wording tests when intentionally changing product behavior; preserve source integrity, arithmetic, migration and factual invariants.
- Some QA scripts are tailored to old coverage and text. For example `scripts/v1-smoke.mjs` describes Cabanga as not covered, while active coverage comes from the generated 72-neighborhood index. The plan should require auditing a test's expectation before calling a failure a regression. Do not mass-delete failing tests.

## Recommended epoch logic

These dependency-based observations informed VE00–VE17 in the official plan; use those VE identifiers for execution rather than the informal numbered phases below.

1. Baseline and acceptance pack: capture current behavior, actual published sources, representative property pairs, inherited failures, and baseline user task success. This should be bounded; do not turn baseline work into another research project.
2. First visible comparison: reuse existing facts to show monthly difference, a useful routine trade-off and the missing fact that could change the choice. Preserve optional personalization. No graph prerequisite for a genuine known-cost comparison.
3. Evidence promotion and acquisition: implement versioned source contracts and the shared evidence ledger; repair misleading GTFS/terrain language at the point of derivation; publish a reproducible compact pilot package with rollback.
4. Entrances, street topology and POIs: create the graph and reconcile reachable everyday destinations, including backup paths. Deliver route-aware essentials as soon as one pilot corridor passes tests, while separately tracking coverage of all five neighborhoods.
5. Time-dependent transport and routine: apply service calendars, day/time/mode, transfers and departure sensitivity; replace the commute approximation where validated. Retain a cheap clear fallback where coverage is absent.
6. Historical rain access: link observed disruptions to edges and recalculate routes under historical scenarios. Evaluate on held-out storm episodes and locations. Do not make a forecast model a prerequisite.
7. Facades and shade: reuse the solar engine, fill Madalena geometry, compare route exposure by time, validate against field samples and measure route detour versus minutes of sun avoided.
8. Evening, crossings, sound and change: combine observed features and dated events, highlight what matters along an actual return route; preserve the distinction between a permit and an active site. If sound is not measured, do not manufacture decibels.
9. Offer history, matched comparables and negotiation: deduplicate real offered units, isolate rent versus sale, measure stratified coverage and leave-one-source-out stability, then add quantiles or a simple model only if it improves the action.
10. Adaptive questions and optional inverse search: choose the least burdensome question that can reverse a decision; offer areas matching a person's routine without requiring a long onboarding form. Evaluate preference sensitivity and explanation comprehension.
11. Integrated pilot and evaluation: five-neighborhood capability coverage, multiple user scenarios, native smoke, refresh failure/rollback, performance, acquisition cost and a moderated task test. Only pass what was observed.
12. Advanced experiments and expansion: multimodal extraction, calibrated flood models, street-image accessibility, remote sensing, AVM/GNN and neighboring-city transfer are separate bounded experiments with baselines, holdouts and kill rules. They must not block the useful pilot.

## Quantitative gates to propose, with clear status

Thresholds in the official plan should be labeled provisional targets, not measurements or promises. Prefer:

- Correctness gates: zero invalid foreign keys or impossible coordinates in promoted bundles; zero known closed/private crossing links in the hand-audited route set; zero silently converted unknown costs.
- Coverage gates: publish a per-neighborhood denominator, accepted, rejected and unassessed counts. Never pass a five-neighborhood feature using only Boa Viagem's volume. A feature can graduate by partition without claiming citywide completeness.
- Value gates: in a small moderated pilot, people can choose which property to visit first, identify the evidence responsible and name a remaining decision-changing question. Report numerator, denominator and observations; a small formative sample is not a statistical outcome guarantee.
- Performance gates: measure cold and warm comparison latency separately, p50/p95 across repeated runs on a named reference device, resident memory and bundle size. No live LLM in the saved-comparison path. Use a per-epoch delta budget until a meaningful device baseline exists.
- Acquisition economics: count useful accepted entities/events rather than HTTP requests; record cost per accepted record, human review minutes, source failure rate, update lag and rejection reasons. Optimize repeated collection cost after usefulness is shown.
- Modeling gates: outperform a frozen simple baseline on held-out buildings, blocks, sources and dates as appropriate; report calibration and abstention/coverage. Use ablation to show whether images or a graph adds value beyond structured data.
- Rollback gates: simulate interrupted generation and unavailable sources. The last good bundle remains loadable and saved user analyses remain intact. Publication should never require editing downloaded source files manually.
